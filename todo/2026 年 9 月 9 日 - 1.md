什么是 长尾问题

---

# chatgpt response

**长尾问题（Long-tail problem）**，简单说就是：

> **大量低频、零散、单个看起来不重要，但加起来占比很大的问题。**

它来自“长尾分布”这个概念。你可以想象一条曲线：

```text
频率
↑
│██████
│████
│██
│█
│ \
│  \
│   \________________________
└────────────────────────────→ 问题种类
   高频头部          大量低频长尾
```

比如你做的**营销活动页面搭建平台**就很典型。

头部问题可能只有几十种，而且天天出现，比如：

- Banner 怎么配置
- 商品列表怎么配置
- 优惠券组件怎么配置
- 图片怎么上传
- 页面怎么发布

这些很好处理，因为规则稳定、数据多、大家都熟悉。

但真正麻烦的是后面这些：

- “这个旧活动为什么在 iOS 15 上有 4px 偏移？”
- “这个组件为什么只在某个业务线允许套两层？”
- “618 去年的会场为什么不能直接复制今年？”
- “这个组件跟另一个组件组合时为什么曝光埋点重复？”
- “某个商家要求标题超过 20 字，但默认 schema 限制 16 字怎么办？”
- “某个 2023 年遗留组件为什么必须先调用 A 接口再调用 B 接口？”

每一种问题可能一年只碰到一两次。

但问题种类可能有 **几百、几千、几万种**。

这就是长尾问题。

---

它在 AI / Agent / RAG 里尤其重要。

比如你之前提到：

> 1000 多个组件，是不是一个组件写一个 Skill？

这里其实很容易遇到长尾问题。

假设有：

```text
1000 个组件
×
每个组件 10 个特殊规则
×
不同业务线
×
不同版本
×
不同组合关系
```

最终可能不是 1000 个问题，而是几万甚至几十万个边界情况。

你不可能把所有东西都提前写成：

```text
if 情况1:
    ...
elif 情况2:
    ...
elif 情况3:
    ...
```

也不太可能：

```text
一个长尾情况 = 一个 Skill
```

否则 Skill 数量会爆炸。

所以实际系统通常会分层处理：

```text
高频、稳定、强规则
        ↓
代码 / Schema / Tool / Workflow

中频、有明确业务知识
        ↓
Skill / SOP / Rule

低频、大量、持续变化
        ↓
RAG / 搜索 / 文档 / 历史案例

极端异常
        ↓
人工介入
```

这也是为什么你前几天问的 **Skill vs RAG**，背后其实就涉及长尾问题。

例如：

> “倪海厦的某个具体观点是什么？”

这种知识非常多，而且用户可能问：

- 某个方剂
- 某个症状
- 某句话
- 某一讲
- 某个病例
- 两种理论的区别

问题空间巨大。

如果全部写进 Skill：

```text
skill:
    知道所有倪海厦知识
```

本质上只是在 Skill 文件里塞了一大坨文本，既难维护，也无法很好处理长尾查询。

更自然的方式通常是：

```text
Skill
= 告诉 Agent “怎么回答中医问题、怎么检索、怎么引用、怎么推理”

RAG
= 存放大量倪海厦原始资料

Tool
= 搜索资料

LLM
= 理解用户当前这个长尾问题
```

所以可以记住一句很实用的话：

> **Skill 更适合解决“怎么做”，RAG 更适合解决“知道什么”，而长尾问题通常迫使系统拥有检索能力。**

不过“长尾”并不等于“不重要”。

比如一个支付系统：

```text
99.9% 请求正常
0.1% 是异常
```

这 0.1% 很长尾，但可能包含：

```text
重复扣款
退款异常
金额精度
并发支付
订单状态错乱
```

频率低，却非常重要。

所以工程上真正困难的往往不是：

> 把 80% 的常见场景做好。

而是：

> **怎么用合理成本覆盖剩下那 20% 千奇百怪的长尾。**

这也是为什么 AI Agent 很有价值：传统软件特别擅长处理**确定性的头部问题**，LLM 则比较擅长理解那些难以提前枚举的**自然语言长尾问题**。

但 LLM 也不能凭空解决长尾，所以最后往往会变成：

```text
用户问题
   ↓
LLM 理解意图
   ↓
这是标准问题吗？
 ┌───────┴────────┐
是                否
↓                 ↓
固定 Tool       检索 / RAG
Workflow          ↓
↓              找相关知识
确定执行            ↓
                LLM 推理
                   ↓
             仍无法处理？
                   ↓
                 人工
```

你现在学习 RAG、Tool Calling、Skill、Agent，其实可以把它们统一放到一个问题下面理解：

> **一个系统如何同时处理高频确定性问题和大量不可预先枚举的长尾问题？**

这个视角会比单独背 RAG、Skill、Tool 的定义更接近真实工程。

一个系统如何同时处理高频确定性问题和大量不可预先枚举的长尾问题？

---

# chatgpt response

核心思路不是“用一种技术全吃掉”，而是**分层处理**：

```text
高频 + 确定
→ 代码 / Schema / Workflow / Tool

中频 + 有明确规则
→ Rule / Skill / SOP

低频 + 知识分散
→ RAG / Search / 历史案例

极端异常 + 高风险
→ 人工兜底
```

可以把它理解成一个“从确定性到开放性”的漏斗。

以你的营销活动页面搭建平台为例。

用户说：

> “帮我创建一个满 99 减 20 的优惠券组件。”

这是高频、确定性强的问题。最适合直接走：

```text
Intent
→ Coupon Tool
→ 校验 Schema
→ 生成合法配置
→ 写入 Page Schema
```

不应该让 LLM 自由发挥，因为这类事情代码可以做得更稳。

但用户又说：

> “去年双十一有个优惠券组件，好像限制过部分会员等级，今年还能这么配吗？”

这就不是纯确定性问题了。系统可能需要：

```text
用户问题
→ 检索去年活动文档
→ 检索会员限制规则
→ 检索该组件历史版本
→ LLM 综合判断
→ 给出建议
```

这里 RAG 就比硬编码合适。

真正成熟的架构通常像这样：

```text
                 用户请求
                    ↓
             Intent / Router
                    ↓
        ┌───────────┼───────────┐
        ↓           ↓           ↓
   确定性任务    知识型问题    模糊复杂任务
        ↓           ↓           ↓
      Tool         RAG       Planner/Agent
        ↓           ↓           ↓
      Schema      Context     多步调用
        ↓           ↓           ↓
        └───────────┴───────────┘
                    ↓
              Validation
                    ↓
              最终结果
                    ↓
             必要时人工兜底
```

这里最关键的不是“Router 很智能”，而是**每一层承担不同职责**。

第一层，代码负责守住确定性。像字段是否合法、组件是否存在、价格是否为负、版本是否兼容，这些不能交给 LLM 猜。

第二层，RAG 负责补充开放世界知识。比如“这个组件以前在哪些活动里用过”“某业务线有什么特殊限制”“历史故障怎么处理”。

第三层，Agent 负责组合。Agent 的价值不是“替代所有代码”，而是决定：

```text
先查什么
再调什么工具
什么时候继续
什么时候停止
```

第四层，Validator 负责最后防线。比如 LLM 最终生成：

```json
{
  "type": "Coupon",
  "discount": -20
}
```

即使前面推理都错了，Schema Validator 也应该直接拦截。

所以一个很重要的工程原则是：

> **LLM 负责理解和决策，代码负责约束和执行。**

这句话对 Agent 系统尤其重要。

再往深一点看，一个系统其实是在做“覆盖率”和“成本”的权衡。

你可以想象：

```text
前 60% 高频问题
→ 直接代码覆盖
→ 成本最低、可靠性最高

接下来 25%
→ Skill / Rule / RAG
→ 成本中等

再后面 10%
→ Agent 推理 + 多步搜索
→ 成本更高

最后 5%
→ 人工
→ 最贵，但不值得自动化
```

而不是：

```text
100% 全交给 Agent
```

这通常会很贵，也不稳定。

你主管说“一个组件一个 Skill”，问题就在这里。假设有 1000 个组件，你实际上还有：

```text
组件
× 版本
× 业务线
× 活动类型
× 组合关系
× 历史兼容
```

Skill 数量很容易失控。

更合理的是：

```text
组件结构
→ Component Registry / Schema

组件能力
→ Tool

组件使用说明
→ RAG

少量稳定操作规范
→ Skill

组件之间关系
→ Metadata / Graph / Rule Engine

最终编排
→ Agent
```

例如你的 Demo，我会建议未来最终长成这种结构：

```text
                    Agent
                      │
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
 Component Tool   Knowledge RAG   Page Tool
        │             │             │
 Component        Docs / Cases    Page Schema
 Registry
        │
 JSON Schema
        │
 Validator
```

假设用户说：

> “给我做一个适合 618 的商品会场，顶部 Banner，下面商品瀑布流，再加优惠券。”

Agent 不应该直接输出一大坨 JSON。

而应该类似：

```text
1. 理解需求
2. 搜索适合 618 的历史模板
3. 查询 Banner 组件能力
4. 查询商品瀑布流组件能力
5. 查询优惠券规则
6. 生成 Page Schema
7. Schema 校验
8. 检查组件兼容性
9. 返回最终页面
```

这就是所谓的：

> **deterministic core + probabilistic edge**

中文可以理解成：

> **确定性核心 + 概率性外围。**

真正关键的业务状态、支付、数据写入、Schema 校验，放在确定性核心里。

自然语言理解、搜索、规划、推荐、长尾问题处理，放到概率性外围。

这是现在很多 Agent 系统比较合理的设计哲学。

你可以顺便记住另外一个非常重要的判断公式：

```text
能不能枚举？
    ↓
能枚举 → Rule / Code

不能枚举，但是能搜索？
    ↓
能搜索 → RAG

不能直接搜索，但需要多步处理？
    ↓
Agent

风险太高 / 信息不足？
    ↓
Human
```

这其实已经可以成为你以后设计 AI 系统时的一个默认框架。

对你现在这个 Demo 来说，我甚至建议你不要从：

> “我要加 RAG / Skill / Agent”

开始设计。

而应该先问：

> **这个问题究竟属于确定性问题，还是长尾问题？**

然后再决定技术。

这一步本身，就是 AI 应用工程师和“只会调用大模型 API”的人之间很大的区别。
